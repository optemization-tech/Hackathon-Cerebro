# Hindsight Indexer Worker — design

The Indexer is the single bridge between Short-Term Memory (Notion) and Hindsight Cloud. It is the only thing in the system that calls Hindsight `retain()`. Source workers stay thin; long-term distillation is the Sync Worker's job.

This doc covers the implementation-level design. For the architectural framing read [cerebro.md §Hindsight Indexer Worker](cerebro.md#hindsight-indexer-worker). For Hindsight per-call parameter semantics read [hindsight-configuration.md §Per-call parameters](hindsight-configuration.md#per-call-parameters-set-by-the-indexer-worker-not-in-bank-config).

## Scope (Phase-1 Minimum)

**In scope:**
- One Notion Worker at `indexer/` (repo root, matching `slack/` and `google/`).
- One `indexerDelta` sync: queries STM for `Status = cleaned`, retains each row in Hindsight (sync mode), flips Status to `indexed` on success or `failed` on error.
- One `reindexStmRow` manual tool: single-row reprocessing for debugging + demo.
- Demo-visible behavior: an STM row that lands `cleaned` should transition to `indexed` within one `indexerDelta` cycle (≤5 min) and the move is observable in the Notion UI.

**Explicitly deferred to V1.1:**
- Retry sync (`indexerRetry`): 30-min cron that re-tries `failed` rows. Deferred because we have no observed failure-mode data yet. The `reindexStmRow` tool is the manual escape hatch.
- STM schema additions (`Failed reason`, `Retry count`): tied to the retry sync. No schema migration in Phase-1.
- Backfill of historic STM rows: focus demo on fresh data; run one-shot via `reindexStmRow` post-demo.

**Out of scope (full product):** anything Sync-Worker-shaped (reading facts back out of Hindsight, writing to Long-Term Memory, classification). The Indexer only writes one direction — STM → Hindsight.

## Status filter (entry point)

The Indexer queries Short-Term Memory rows by `Status` value. The canonical values are:

| Status | Written by | Meaning |
|---|---|---|
| `cleaned` | Source workers (slack, google, meetings-ingest after patch) | Source has parsed + cleaned the input and written it to STM. Ready for Hindsight retain. |
| `indexed` | `indexerDelta` on success | Indexer has called Hindsight `retain()` successfully (sync mode — extraction complete). Sync Worker picks up from here. |
| `failed` | `indexerDelta` on error | Hindsight `retain()` errored. Error is logged to console. Use `reindexStmRow` tool to retry. |
| `distilled` | Cerebro Sync Worker (downstream) | Sync Worker has projected facts into Long-Term Memory. |

The canonical Status is `cleaned`. The `cerebro.md` spec previously used `pending` — that has been reconciled. Slack ([slack/src/index.ts:182](../../slack/src/index.ts)) and google ([google/src/index.ts:381](../../google/src/index.ts)) both write `cleaned`. Meetings-ingest needs a one-line patch (U4).

**Dependency:** meetings-ingest ([workers/meetings-ingest/src/index.ts](../../workers/meetings-ingest/src/index.ts)) does not currently write a Status value. One-line patch required before the Indexer can pick up meeting-transcript rows: `Status: { select: { name: "cleaned" } }` in the page-creation properties.


## Architecture

```
┌──────────────────────────────────────────────────────────┐
│  indexer/ (Notion Worker) — Phase-1 Minimum              │
│                                                          │
│  ┌────────────────────────────────────────────────────┐ │
│  │ sync: indexerDelta                                 │ │
│  │ filter: Status = cleaned                           │ │
│  │ schedule: 5m  ·  batch: 50                         │ │
│  └────────────────────────┬───────────────────────────┘ │
│                            │  processStmRow()            │
│                            ▼                             │
│  ┌────────────────────────────────────────────────────┐ │
│  │ pacer: hindsightApi (10 req/s)                     │ │
│  └────────────────────────────────────────────────────┘ │
│                                                          │
│  ┌────────────────────────────────────────────────────┐ │
│  │ tool: reindexStmRow (manual single-row, by pageId) │ │
│  └────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────┘
```

Both syncs and the tool route through one `processStmRow(notion, stmPageId)` helper. Single source of truth for row processing.

The `indexerSyncShim` managed database is a scheduler hook only — never written. Same pattern as [slack/src/index.ts:572](../../slack/src/index.ts).

## src/index.ts — module layout

Top-to-bottom:

1. **Constants:** `STM_DATA_SOURCE_ID`, `HINDSIGHT_BANK_ID = "Cerebro"`, `DELTA_BATCH = 50`.
2. **`worker.database("indexerSyncShim", …)`** — scheduler hook only.
3. **`worker.pacer("hindsightApi", { allowedRequests: 10, intervalMs: 1000 })`** — conservative default. Tune up once Hindsight Cloud rate limits are known.
4. **`callHindsightRetain(payload)`** — raw `fetch` POST to `${HINDSIGHT_API_URL}/v1/${NAMESPACE}/banks/${BANK_ID}/memories`. Bearer auth via `HINDSIGHT_API_KEY`. Matches the pattern in [scripts/setup-hindsight.mjs](../../scripts/setup-hindsight.mjs).
5. **`readStmRow(notion, pageId)`** — fetches row properties + assembles page body text from block plain_text (no markdown round-trip; Hindsight only needs text content).
6. **`buildTagsForRow(row)`** — per [cerebro.md §Tagging strategy](cerebro.md).
7. **`buildContextForRow(row)`** — per [hindsight-configuration.md §`context`](hindsight-configuration.md). Shape: `"<Data Type> from <Source> by <Person Source>"`.
8. **`processStmRow(notion, pageId)`** — orchestrates: read → build tags+context → pacer.wait → retain (sync) → flipStatus. On Hindsight error: flip to `failed`, log, continue.
9. **`queryStmRowsByStatus(notion, statuses, limit)`** — paginated `notion.dataSources.query`.
10. **`flipStatus(notion, pageId, nextStatus)`** — transitions to `indexed` or `failed`.
11. **`worker.sync("indexerDelta", …)`** — sole sync, see below.
12. **`worker.tool("reindexStmRow", { schema: { stmPageId: string } })`** — single-row invocation.

## Per-row data flow

```
STM row (Status: cleaned)
  │
  ▼ indexerDelta picks up row
processStmRow(notion, pageId)
  │
  ├─ readStmRow → { stmId, dataType, source, personSource, createdTime, entities, bodyText }
  ├─ buildTags → ["team:optemization", "source:slack", "data-type:slack-message", "stm:<id>", …]
  ├─ buildContext → "Slack message from Slack by Tem"
  ├─ pacer.wait()
  ├─ callHindsightRetain({
  │     bank_id, content: bodyText, document_id: stmId, tags, context,
  │     timestamp: createdTime, entities: row.entities ?? [], async: false
  │   })
  │     ├─ HTTP 200 → flipStatus(pageId, "indexed")
  │     └─ HTTP error → flipStatus(pageId, "failed"), console.error(err)
  └─ console.log({ stmId, pageId, durationMs, outcome })
```

## Error semantics (Phase-1 Minimum)

- **Success:** Status → `indexed`. Hindsight extraction has completed (sync retain — HTTP 200 means extracted).
- **Failure:** Status → `failed`. Error logged to console. Row stays `failed` until a human resets it via `reindexStmRow` or by manually flipping Status back to `cleaned` in the Notion UI.
- **Idempotency:** `document_id = stmId` means re-running over the same row upserts in Hindsight — no duplicates.

## Hindsight retain call

**Endpoint:** `POST https://api.hindsight.vectorize.io/v1/default/banks/{bank_id}/memories`. Confirmed against the live OpenAPI spec at `https://api.hindsight.vectorize.io/openapi.json` on 2026-05-17. Earlier descriptions in [cerebro.md:427](cerebro.md) and [hindsight-configuration.md:242](hindsight-configuration.md) refer to a `retain(…)` SDK method — the Python/TS SDKs wrap this REST endpoint. The namespace segment is literally `default` (not parameterized).

**Request body:** `RetainRequest` — an `items` array plus async flag. Each item is a `MemoryItem`. Item-level fields include `content`, `context`, `timestamp`, `document_id`, `tags`, `entities`, `metadata`, `observation_scopes`, `strategy`.

```typescript
await fetch(`${HINDSIGHT_API_URL}/v1/default/banks/${encodeURIComponent(BANK_ID)}/memories`, {
  method: "POST",
  headers: {
    Authorization: `Bearer ${HINDSIGHT_API_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    items: [{
      content: row.bodyText,
      context: `${row.dataType} from ${row.source} by ${row.personSourceName}`,
      timestamp: row.createdTime,        // ISO-8601 from Notion created_time
      document_id: row.stmId,            // STM `ID` property value (visible in Notion column); falls back to row.pageId
      tags: [
        "team:optemization",
        `person-source:${row.personSourceSlug}`,
        `source:${row.source.toLowerCase()}`,
        `data-type:${row.dataType.toLowerCase().replace(/ /g, "-")}`,
        `stm:${row.stmId}`,
        ...(row.engagement ? [`engagement:${row.engagement}`] : []),
        ...(row.verified ? ["verified:true"] : []),
      ],
      entities: row.entities ?? [],      // empty until clean() lib ships
      // observation_scopes: "per_tag"   // recommended by hindsight-configuration.md
    }],
    async: false,                         // sync mode: HTTP 200 means extraction complete; Status flip is honest
  }),
});
```

**Response shape (HTTP 200 on success):**

```json
{
  "success": true,
  "bank_id": "Cerebro",
  "items_count": 1,
  "async": false,
  "operation_id": null,
  "usage": { "prompt_tokens": 420, "completion_tokens": 85 }
}
```

With `async: false` (sync mode), the retain call blocks until Hindsight has actually extracted memory units. `usage` is populated. The Indexer flips Status to `indexed` only after HTTP 200 — so `indexed` means extraction actually ran, not just "queued." This is ~3s per row but gives honest Status semantics for the Sync Worker downstream.

**Batching opportunity:** The `items` array supports multiple memories per call. The Indexer's per-cycle batch (50 rows) could be a single POST instead of 50 sequential POSTs. Defer to V1.1 — for V1 we keep one-row-per-POST to preserve per-row error isolation (a single bad row in a batch may fail the whole call depending on Hindsight's semantics — needs verification).

**`document_id = stmId`** is the load-bearing idempotency primitive. Using the STM `ID` property value (rather than the Notion page ID) means the Hindsight `Document ID` matches what humans see in the Notion `ID` column — symmetric cross-reference between the two systems. Re-running the Indexer over the same row updates the Hindsight memory in place rather than accumulating duplicates. Random UUIDs would create a fresh fact set per call — explicitly called out as an anti-pattern in [hindsight-configuration.md:331](hindsight-configuration.md).

**Why STM `ID` over Notion page ID** (decision 2026-05-17 during prototype):
- STM `ID` is visible in the Notion column — humans can search either system using the same string.
- It's already deterministic per source worker (slack uuidv5, google/meetings-ingest hashes), so idempotency holds.
- The Notion page ID isn't visible in any Notion column — humans would have to dig the URL out of the page settings to cross-reference.
- Trade-off lost: page ID could resolve directly to a `notion.so/<workspace>/<id>` URL. Citations in Ask Cerebro can still resolve STM `ID` to a Notion URL by doing a one-shot `dataSources.query({ filter: { property: "ID", rich_text: { equals: <stm-id> } } })` — one extra API call per citation, cheap.
- Fallback: when the STM `ID` property is empty (shouldn't happen — all three source workers write it — but defensive), the Indexer falls back to `page.id`.

## Reading STM row properties

The `processStmRow` pipeline consumes a normalized row shape:

| Field | Source | Notes |
|---|---|---|
| `pageId` | `page.id` | Notion's canonical page identifier. Used as last-resort fallback for `document_id`. |
| `stmId` | `ID` rich_text property | **Primary identifier** — used as Hindsight `document_id` and in the `stm:<id>` tag. This is the value visible in the Notion `ID` column. Source-deterministic (slack: `uuidv5("slack://team/channel/ts")`; google/meetings-ingest: hash of source event ID). |
| `bodyText` | `notion.blocks.children.list` walk | Concat block `plain_text`. See "Body content" below. |
| `dataType` | `Data Type` select property | E.g. `"Slack message"`, `"Email"`, `"Calendar event"`. |
| `source` | `Source` **select** property if present; otherwise inferred from `Data Type` via a small map; otherwise `"unknown"`. | Read via `getSelect("Source")` — NOT `getRichText`. Source is a select field per the STM schema. |
| `personSource` | First user in `Person Source` people-relation. Display name. | Falls back to `"unknown"` when empty. |
| `personSourceSlug` | Lookup table from Person Source user email → slug. | V1 has a hardcoded map (e.g. `tem@optemization.com → tem`). Small team makes this fine. |
| `createdTime` | Built-in Notion `created_time` of the page. | ISO-8601. See "Timestamp caveat" below. |
| `entities` | `Entities` rich_text property parsed as JSON. | Empty array if missing/malformed. |
| `verified` | `Verified` checkbox property if present. | Defaults false. Only Notion-Docs rows set this (worker not yet built). |
| `engagement` | `Engagement` select property if present. | Optional; omitted from tags when empty. |

### `Source` inference map

When the `Source` property is missing (current state for slack/google rows), derive from `Data Type`:

| `Data Type` | Inferred `source` |
|---|---|
| `Slack message` | `slack` |
| `Email` | `gmail` |
| `Calendar event` | `gcal` |
| `Meeting transcript` | `granola` (default — refine once Circleback worker ships) |
| anything else | `unknown` |

Source workers should eventually write `Source` explicitly so the Indexer doesn't have to infer. Tracked as a follow-up.

### Timestamp caveat

[hindsight-configuration.md §`timestamp`](hindsight-configuration.md#timestamp-required-for-temporal-retrieval) says we should pass the **source event time**, not the ingestion time, so temporal recall ("what happened last week?") ranks correctly. Today our STM rows only carry Notion's `created_time` (which equals ingestion time). For a Slack message ingested two weeks late, `created_time` is wrong.

V1: use `created_time` as a pragmatic approximation. Acceptable because the demo runs against fresh data — ingestion time ≈ source time within minutes.

Follow-up: add a `Source timestamp` date property to STM and have source workers populate it from the source system (Slack message ts, calendar event start, email date header). The Indexer reads this property when present and falls back to `created_time` otherwise.

## Body content

The STM row's page body is the text Hindsight indexes. Read via `notion.blocks.children.list(pageId)` and concatenate the `plain_text` of each block. No markdown round-trip — Hindsight's extraction LLM doesn't need formatting markers.

Assumption: source workers write **flat block structure** (no nested toggles/callouts/columns). slack ([slack/src/index.ts:136](../../slack/src/index.ts)) and google both write flat markdown that lowers to flat blocks. If a future source worker writes nested blocks, the Indexer needs a recursive walk — flagged in implementation comments.

Pagination: walk `has_more` until exhausted. For very long pages (>100 blocks) this is a few extra Notion calls per row; well under budget.

## Manual tool: `reindexStmRow`

```typescript
worker.tool("reindexStmRow", {
  title: "Re-index Short-Term Memory Row",
  description: "Force a single STM row through the Hindsight retain pipeline, regardless of its current Status. Used for testing, debugging, and live demo reruns.",
  schema: j.object({ stmPageId: j.string().describe("Notion page ID of the STM row to re-index.") }),
  outputSchema: j.object({
    pageId: j.string(),
    previousStatus: j.string(),
    nextStatus: j.string(),
    error: j.string().nullable(),
  }),
  execute: async ({ stmPageId }, { notion }) => {
    /* calls processStmRow, returns the transition outcome */
  },
});
```

Invocation:

```shell
ntn workers exec reindexStmRow --local -d '{"stmPageId":"362a4866-..."}'
```

Useful for:
- Sunday demo reruns ("watch this Slack message land in Hindsight").
- Testing individual rows without waiting for the 5-min cycle.
- Letting teammates dogfood the pipeline from CLI without Notion-UI ceremony.

## Pacer budget

`hindsightApi` shared by both syncs. With `allowedRequests: 10, intervalMs: 1000` and two syncs sharing, each gets ~5 rps. At a 50-row batch that's ~10 seconds of indexing per cycle — well under the 5-minute window. If Hindsight Cloud documents higher limits, bump to 20-30 rps.

## Logging + observability

- Per-row: `console.log(JSON.stringify({ stmPageId, dataType, source, outcome, durationMs }))`.
- Sync summary at end of each cycle: counts of `processed`, `indexed`, `failed`, `skipped`.
- Errors retain full Hindsight HTTP body in `console.error` for debugging; only the first 500 chars land in `Failed reason`.

Read via `ntn workers runs logs <runId>` or `ntn workers runs list --plain | grep indexer`.

| Test | Command | Expected |
|---|---|---|

| Manual recovery | Restore key, run `reindexStmRow` for the failed row | Row flips back to `indexed` |
| Backfill drill | Flip 10 `indexed` rows back to `cleaned` in Notion UI | Next delta cycle re-indexes them; Hindsight memory upserts in place (no duplicates) |

No unit test framework — same posture as the other workers. Correctness check is `npm run check` (`tsc --noEmit`) + the exec scripts above.

## What this design deliberately does not include

- **Webhook ingress.** The Indexer is poll-driven, not pushed to by Notion. Notion's webhook capability is reserved for the Sync Worker.
- **Backpressure to source workers.** If Hindsight Cloud is fully down, rows accumulate in `failed`. We do not pause source workers — source ingestion is decoupled from indexing on purpose. Recovery is via `reindexStmRow` tool.
- **Hindsight SDK abstraction.** Raw `fetch` is fine for V1. If we ever swap memory engines, we rewrite this one worker — same argument as [cerebro.md §Why a single Worker](cerebro.md#why-a-single-worker-not-per-source).
- **Per-source pacers.** One Hindsight pacer covers everything. We're not rate-limiting by source.
- **Schema enforcement on the Entities property.** The Indexer reads whatever JSON is there and passes it through; malformed/missing → empty array.
